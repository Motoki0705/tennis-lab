# Coding Conventions

## 1. Python コーディングスタイル

- **フォーマッタ**
  - コード整形には `black` を使用します。
  - インポート整形には `isort` を使用します。
- **命名規則**
  - クラス名: `CamelCase`（例: `BallTracker`）
  - 関数・メソッド・変数名: `snake_case`（例: `load_config`, `ball_positions`）
  - 定数: `UPPER_SNAKE_CASE`（例: `DEFAULT_FPS`）
- **その他**
  - 1 行の長さは 88 文字を目安にします。
  - インデントはスペース 4 個とします。

## 2. 型ヒント / ドキュメンテーション

- **型ヒント**
  - 新しく追加する関数・メソッドには、原則として**すべて型ヒントを付けます**。
  - 既存コードを変更する場合も、可能な範囲で型ヒントを追加します。
- **docstring**
  - 外部から呼ばれるクラス・関数には docstring（google style） を付けます。
  - 引数・返り値・重要な副作用（例: ファイル書き込み）があれば簡潔に記載します。

## 3. プロジェクト構造 / 依存関係

- **ディレクトリの役割**
  - `src/utils`: 共通で再利用可能なユーティリティ関数・クラスを置きます。
  - `src/base`: 他モジュールから利用される基盤となるクラス・インターフェースを置きます。
  - `src/blcs`, `src/plcs`: それぞれの機能領域ごとの実装を置きます。
- **依存関係の方向**
  - `utils` は他のモジュールに依存しないようにします。
  - 上位レイヤー（アプリケーション側）から下位レイヤー（base, utils）を利用し、逆方向の依存は避けます。

## 4. ロギング / 例外処理

- **ロギング**
  - デバッグや情報出力には `print` ではなく `logging` を使用します。
  - 重要なイベント（学習開始・終了、エラー発生など）は `info` / `warning` / `error` でログに残します。
- **例外処理**
  - 想定外の状態には `assert` ではなく適切な例外クラスを使います（例: `ValueError`, `RuntimeError`）。
  - 例外を握りつぶさず、ログにエラーメッセージと原因が分かる情報を残します。
