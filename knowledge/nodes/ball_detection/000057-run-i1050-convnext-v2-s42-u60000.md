GPU smoke 96更新は成功したが、本学習はepoch 0の5,800更新を最後の記録としてCUDA unknown errorで異常終了した。最後のloss/gradient normはfiniteで、nonfinite gradientを検出して停止したログではない。最初のvalidation・checkpointに到達しておらず、再開可能な重みも全validation精度もない。frontmatterのglobal_stepは最後のログで確認できた更新数であり、障害直前の正確な更新番号ではない。TensorBoardなし。

clip_grad_norm_の判定でエラーが表面化し、先読みgeneratorの終了時synchronizeとallocatorでもCUDA error、child processがSIGABRT、outer queueがexit 1となった。baselineの初回停止はepoch 2の保存後だったが、今回の停止はepoch途中なので「epoch境界だけの問題」という説明は支持されない。20:32 JST時点で別候補FasterNetは最初のvalidationを通過している。

共通のnvJPEG/先読み/compile/CUDA経路は原因候補だが、ログだけで原因を特定できない。Windows System logの障害時刻近傍にGPU resetを示すイベントは確認できなかった。NVIDIAの[cudaErrorUnknown定義](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__TYPES.html)も原因を特定しない。使用版torchvision 0.28.0の[nvJPEG実装](https://raw.githubusercontent.com/pytorch/vision/v0.28.0/torchvision/csrc/io/image/cuda/decode_jpegs_cuda.cpp)には内部streamと同期があり、現行画像準備側にもcaller stream fenceが存在する。この調査はライブラリの不具合を証明しない。

次は同じモデル・データ・BF16・seed・学習率を保ち、画像先読みだけを外すserial nvJPEGを新run名で試す。最初の1epochを60000更新用LRのまま実行し、validation/保存とプロセス終了を検証する。成功時のみ同じcheckpointから残りを続ける。1epochの成功は長期安定性の証明ではなく、全6万更新まで継続して観測する。今回の失敗runを削除・成功扱いにはしない。先読み方式が異なるrun間の速度差をCNN単体の効果とは解釈しない。
