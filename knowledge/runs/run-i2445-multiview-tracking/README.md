# Meijiの3D人物追跡と選手選別

[#2444の確定版](../run-multiview-pose-link-recall-20261124/README.md)を入力に、開発用Meiji 3cam 4本を人手ラベルで採点し、meiji_4camの69本で選別と3Dの被覆を確認した。実装と成果物の軸は[時間追跡のREADME](../../../src/tennis_scene/multiview_tracking/README.md)に記載した。

## 窓と選別規則の根拠

- 4camの000・020・037・058で、選別領域の候補から時間差1フレームの最寄り3D胴体中心までの水平距離を集計した。clip別のP95は0.042〜0.067 m。8フレーム差では0.322〜0.542 m、24フレーム差では0.933〜1.955 mだった。これは最近傍の距離で、異なる人物が最寄りになる場合も含む。
- 3cam開発用で、1フレーム差に同じ遠側選手のラベルが付いた候補を比較した。フレームごとにIoU 0.5以上で照合したDINO行の票が最多の候補を使い、同票ではCの対応スコアが高い方を取った。共通する胴体関節の移動ベクトルのノルムの中央値は、同じ支持カメラ集合で0.025〜0.032 m、支持集合が変わると0.129〜0.882 mだった。切替の際に位置と形状の許容幅を広げ、速度の計算には同じカメラ集合の両端を使った。対応誤りや校正の影響を含むため、この値は真の人体速度の分布と区別する。
- 020では、支持が4台から3台へ移るとき、旧試作が近傍に骨格のあるフレームを飛ばして正側2人を別のIDに分けた。欠測リンクの費用と支持切替の許容幅を調整した後、どちらも元の651フレームを同じIDでつないだ。
- 60fps相当で欠測24フレーム、速度の参照10フレーム、確定30フレーム、先読み42フレームを含む72フレーム窓を使った。観測が再び得られるまでの時間と、その後の局所速度を先読み内に収める。開発用で欠測上限を0.55、0.60、0.80秒に延ばした試行では、選別後のIDF1とfragmentの変化はクリップごとに異なり、000/000の正側不足が続いた。公開設定は0.4秒で固定した。
- 選別領域と滞在要件は #2440 の採用条件と同じ、横5.485 m、縦16.885 m、全長の25%。既存経路の比較では、幅を広げると020・058が復帰し、滞在だけを短くする条件では開発用シングルスで非選手が212 box増えた。3D軌跡も25%を求め、観測の滞在数を順位の主成分にした。運動は最大10%の加点とし、定位置に立つ選手の資格を認める。 [幅と滞在の比較 PR #2450](https://github.com/Motoki0705/tennis-lab/pull/2450)

## Meiji 3camの人手ラベル

#2444と同じ開発用の4 clip、全3,497元フレームを採点した。再投影した実測の肩・腰を各カメラのViTPose全行に一対一で照合した。画像内かつscore 0.25以上の共通点が2つ以上、距離の中央値が1080p換算24 px以下の組を使う。選手IDが付いた行のDINO boxを、人手ラベルとカメラ・フレームごとにIoU 0.5以上で照合した。既存採点器でラベルの同一人物・同フレームの重複を1単位にまとめ、IDF1はclip・カメラごとのID対応後に合算した。選別のprecisionは既知の選手・非選手、recallは全ラベル付き選手の単位を分母にした。未照合の選別予測20件を別に記録した。 [採点器](../../../src/tasks/person_tracking/evaluation.py)・[全クリップ・カメラ別の結果](meiji3.json)

| 射影した対象 | IDF1 | Switch | Fragment | 選手単位のprecision | Recall |
| --- | ---: | ---: | ---: | ---: | ---: |
| 選別したID | 76.09% | 0 | 190 | 99.94% (12,629 / 12,636) | 61.43% (12,629 / 20,558) |
| 全ID、選手ラベルの単位で集計 | 68.34% | 741 | 182 | — | — |

元の支持行へIDを戻す集計では選別後IDF1 77.14%、switch 0、fragment 185、precision 99.95%、recall 62.81%。射影した対象にはCがその視点を支持に使わなかった骨格も含まれ、再投影・2D照合で支持行集計と差が生じる。補間した関節は両集計の対象外。

各side1人を選んだのは4本中3本。000/000の正側で最長の領域内滞在は229フレームで、必要な253に届かなかった。残りの開発用でも遠側のトラックに断片が残るため、選別後のswitch 0は全選手のIDを保った証拠にはならない。CPUで入力照合とCの復元を含めて68.86秒、プロセスの最大RSSは986,780 KiB。 [入力の版と観測数](meiji3.json)

## meiji_4camの保存と被覆

入力は #2444 の再計測に使った69本の候補。CPU 1プロセスで候補読込、追跡、選別、公開・読戻しに102.73秒、最大RSSは990,568 KiB。全69本で両側2 IDを選んだ。選別IDの3D実測は182,357人フレーム、補間は291人フレーム。46,228元フレームのうち4人の実測は43,726、補間を含め4人分が揃うのは43,966。人数と被覆は幾何と選別結果の集計で、IDと選手かどうかの正解は横並び比較で評価する。 [全クリップの条件・成果物ID・診断](meiji4.json)・[比較ページ #2459](https://github.com/Motoki0705/tennis-lab/issues/2459)

| clip | 負側ID | 正側ID | 4人の実測フレーム | #2440で落ちていた正側アレー相当の軌跡 |
| --- | --- | --- | ---: | --- |
| 020 | 0, 4 | 6, 7 | 651 / 651 | ID 6、胴体中心の中央値 `(4.974, 13.901) m`、アレー内の実測474 |
| 058 | 0, 3 | 1, 4 | 765 / 765 | ID 4、胴体中心の中央値 `(4.610, 12.191) m`、アレー内の実測590 |

両clipで通常CLIから別storeに再生成し、成果物IDと記述子SHA、実測座標・関節mask・元観測行が一致した。選別IDの実測に補間は含めていない。clip全体の診断では、020は再出現156、消失31、時間リンクの実測接戦8件。058は再出現327、消失55、時間リンクの実測接戦5件。選別対象外の人物もこの診断に含む。

## 予約未見3 clip

対象は `video_000/clip_002`、`video_001/clip_003`、`video_002/clip_003`。 #2444が確保した38,421行のViTPose計画と、親が承認した001/003の校正補完を使う。ローカルのGPUロックは `r+b` openで `PermissionError`、9カメラのpose完了記録が欠ける。採点入口は完了前に終了値1で止まり、採点開始記録の作成も人物ラベルの採点も0回だった。 [前段の固定計画と復旧手順](../run-multiview-pose-link-recall-20261124/README.md#予約した未見3-clip)

ViTPose完了後に `reproduce.sh holdout` を1回実行する。 [固定設定と採点器のdigest](reserved-protocol.json) と #2444の入力の版を照合し、全3 clipの予測が揃った時点で `outputs/i2445/holdout/scoring-attempt.json` を排他的に作る。3本全体と校正補完clipを除く2本の採点を同時に記録する。

## 再現と成果物

```bash
bash knowledge/runs/run-i2445-multiview-tracking/reproduce.sh all
```

リポジトリrootで実行する。Python 3.11.15、NumPy 2.3.5、SciPy 1.17.1。 #2444 workerの `outputs/i2444` が別の場所にある場合は `MEIJI_POSE_WORKER_OUTPUTS`、Meiji 3camの保存入力を置いた旧outputsのrootは `MEIJI_POSE_ARCHIVED_OUTPUTS` を指定する。

出力は #2445 のworktreeにある `outputs/i2445/meiji3.json` と `outputs/i2445/meiji4/metrics.json`。 #2446が読めるclip storeは `outputs/i2445/meiji4/video_000/<clip>/scene.json` で、`multiview_pose_tracks` v1の記述子と配列はそのstore内にある。Gitには小さな集計と再現コードを保存した。
