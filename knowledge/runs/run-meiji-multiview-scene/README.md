# Meijiの3D時間IDからの身体復元と新旧比較

meiji_4cam 69本に `multiview_3d_tracking` を明示して、時間IDを元のDINO検出行・ViTPose観測に結び付け、HMR2、GVHMR、身体配置を経てSceneResultを出力した。旧経路には #2458 のボール統合済み採用シーンを使った。新経路は同じカメラ幾何とボールを引き継ぎ、独立した出力先に保存した。 [recipeの構成・CLI](../../../src/tennis_scene/multiview_scene/README.md) · [選手枠統合](../run-i2445-player-slot-integration/README.md)

## meiji_4cam 69本

完了基準は、負側・正側それぞれに指定の2人が選ばれ、各IDに1フレーム以上のGVHMR身体と有効な配置があり、SceneResultに1フレーム以上の有効な球3Dが入っていること。元フレームの同時配置率は別に記録した。最小値16.31%の `clip_016` も四人全員の復元と球を確認できるため「完了」に数えた。この基準はclip単位で選手とボールを利用できる条件であり、全フレームの復元や精度の採否は同時配置率と比較動画で評価する。

GVHMRは約30 fpsの実サンプル位置を元フレーム番号で数えた。配置は元フレームの `player_smpl_valid` を使う。旧経路は停止14本でも球を持つ。球の欠測は両方式とも `clip_064` の270フレーム（982/1,252が有効）。新経路で同時配置の割合が最も低い3本は `clip_016` 198/1,214、`clip_013` 195/469、`clip_014` 253/463。 [旧経路の完了表](legacy-completion.csv) · [新経路の完了表](multiview-completion.csv) · [集計の全数値](meiji4.json)

旧経路で完了基準を満たさなかった17本の理由を示す。

| 理由 | clip |
| --- | --- |
| 選手選別で次点が接近 | `002`・`004`・`014`・`018`・`023`・`028`・`036`・`038`・`039` |
| 片側で選手人数が不足 | `020`・`058` |
| 人物対応の候補が接近 | `049`・`060` |
| コート方向の幾何支持が不足 | `012` |
| 選手IDの一部で有効な身体配置が0フレーム | `001`・`005`・`032` |

残差は、採用IDに対応した2D関節のうち、該当3D関節の推定にinlierとして入らなかったカメラで測る。カメラは他の関節にも使われ、両方式が対応付けた関節集合や外れ値判定も異なる。固定カメラを丸ごと外した独立評価と、人手の3D正解での精度検証は未実施。残差中央値の上昇は、被覆の増加と併せて確認する。

両経路で同じ人手ラベルのSHA-256と、選手・非選手の参照単位数を照合した。開発4本は同じr7プランの保存済み採点を参照し、未見は旧経路の採点単位を読み戻して再集計した。旧は選別後の対応グループの2Dトラック、新は選別後の3D骨格をカメラへ射影した時間IDを人手boxに照合した。時間IDはclip・カメラごとに対応付け、同じ参照単位とIoU 0.5で集計する。precisionは選手と非選手に照合できた採用単位から求める。新の補間骨格は採点対象外。対応できなかった予測は [#2445の集計](../run-i2445-reserved-tracking/meiji3.json) に記録される。

未見3本の旧 `001/003` は校正で停止した。新の同clipは校正補完済み入力を使用したため、共通の残り2本も示した。旧の選別recallとIDF1は両集計で高く、新のfragmentも多かった。この比較は時間IDと選別の段階を評価し、3camでのGVHMR・身体配置は未計測。 [集計と入力ハッシュ](meiji3.json) · [予約未見の実行記録](../run-i2445-reserved-tracking/README.md)

## 比較ページ

段階1と段階2を同じ16本で切り替えられる。初回停止14本とseed 42で選んだ成功2本を含む。
段階2は統合版の時間ID、選手の選別、実測と補間、追跡イベントに加え、配置が有効なGVHMR身体の白い輪郭を両方式の四視点に表示する。ヘッダーの `SMPL` は表示時点の有効人数。
`clip_020` では旧経路の片側人数不足と、新経路の4人有効配置606/651フレームを見比べられる。

出力先は実装worktreeの `outputs/pose-comparison-bodies/index.html`。H.264は32本、最大4,190,202 bytes、自己完結のページ全体は63,271,542 bytes。段階1の動画とポスターを元の版とSHA-256で照合した。
各stageのclip・フレーム数、動画・ポスター、HTMLと検証用manifestのSHA-256を記録した。 [動画一覧と検証記録](comparison-page.json)

## 実行

GPUの実行HEADは `01421ac96bbf9472258a930d42c8688c1d546ae0`。全69本を1ジョブで共有queueから実行した。完了記録上はbody選択からSceneResultまで67本を実行し、2本はパイロットを再利用した。 [queue再現コマンド](repro.sh) · [実行情報](run.json)

記録用checkoutから次を実行する。worktreeの配置が異なる場合は `MEIJI_WORKTREES`、旧Meiji 3cam集計の保存先が異なる場合は `MEIJI_ARCHIVE` を指定する。 `MEIJI_REVIEW_OUTPUT` と `MEIJI_PAGE_OUTPUT` は読み戻し結果と自己完結の比較ページの出力先を指定する。

```bash
bash knowledge/runs/run-meiji-multiview-scene/review.sh all
```

`scores`、`verify`、`render` で各処理を個別に実行できる。 `verify` では元の採用参照、新exportのSHA-256、球5配列、身体配置mask、両方の完了表を照合する。 `render` は元の段階1の動画を再利用し、段階2を同じ16本・フレーム間隔で統合版の時間IDから描画する。左右の四視点に有効な身体の白い輪郭、ヘッダーに有効な人数を表示する。既定のページ出力は実装worktreeの `outputs/pose-comparison-bodies` で、作り直すときは新しい出力先を指定する。

ローカル検証ジョブ `20261124T100319Z_0e179f3398ad_i2446-verify-and-render` は908.447秒、終了値0。全69本の採用参照と新旧の球5配列、SceneResultの身体配置maskと両方の完了表を照合した。 [各clipの方式・採用参照・exportのSHA-256](verified-scenes.json)

ページの受領確認は `check_page.py` に、新しいページを `--page`、元の比較ページを `--original` で渡す。 `--output` を指定すると動画一覧とSHA-256を再生成する。
