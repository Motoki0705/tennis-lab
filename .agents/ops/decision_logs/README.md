# Parent decision records

[日本語](README.ja.md) · [简体中文](README.zh-CN.md)

This package defines the shared version 1 contract for captured results, parent
decisions, actions and corrections. It stores private snapshots and prepares safe
publication units. Capture adapters observe existing parent, runner and review
operations, batched Git publication and deterministic navigation READMEs.
Recording grants no execution authority and does not decide task acceptance.

## Contract and ownership

Code is authoritative; the field sets, enums and validators are not duplicated
here. Existing [worker logs](../worker_logs/README.md) retain their three-file
format. Their schema helpers, `Guard`, strict JSON decoder, flock and durable
atomic writer are reused directly.

| Module | Consumer contract |
|---|---|
| [schema.py](schema.py) | `new_id()`, `validate_record()`, `json_bytes()`; exact versioned fields and tagged missing values |
| [graph.py](graph.py) | `validate_graph()`, `references()`, `states()`; typed references, DAG, action history and explicit verification |
| [journal.py](journal.py) | `Journal`; immutable captures and append-only preparation/publication history |
| [projection.py](projection.py) | `render()`, `validate_public()`; the publication envelope `{record, sanitization}` |
| [aggregation.py](aggregation.py) | `aggregate()`; display groups referencing all original records |
| [navigation.py](navigation.py) | `generate()` and `validate_links()`; pure hierarchy generation and link checking |
| [publication_policy.py](publication_policy.py) | Separate addition-only exception, exact regenerated bytes and PR identity |
| [publication.py](publication.py), [publication_state.py](publication_state.py) | Explicit publication, private batches and response-loss reconciliation |
| [capture.py](capture.py) | Private outboxes, causal action snapshots, status and capture-only replay |
| [parent_commands.py](parent_commands.py), [parent_sources.py](parent_sources.py) | Parent CLI decisions, command outcomes, canonical comments and explicit verification |
| [observations.py](observations.py), [review_capture.py](review_capture.py) | Existing runner, dispatcher, worker-log, retrieval, review and merge facts |

Each record has a random UUID4 hex ID, kind, scope, three distinct times and typed
data. Scope carries the repository, parent, nullable child issue, public activity
key, existing worker delegation key/turn and nullable public review key. Direct
parent work needs no invented child issue. New IDs and keys must use `new_id()`;
private session/run IDs and delivery keys never determine public IDs. Their
association exists only in capture entries' private context.

`validate_record()` checks exact keys and types, including nested objects;
serialized input uses the shared duplicate-key-rejecting decoder.
`validate_graph()` additionally rejects missing/wrong-kind references, cross-parent
references, cycles, conflicting action histories and mismatched decision plans.
References express causality independently of timestamps. A graph can branch
from one result to several decisions/actions and join several results in a decision.

## Results, decisions and lifecycle

Results distinguish machine observation, worker report and parent verification.
Runtime completion, artifact quality, CI, final-report availability and publication
are separate observations. No file's existence proves parent receipt or acceptance.
Explicit parent verification is a result whose `verifies` references the checked
results. `states()` derives undecided/unverified states from those references.

Each result compares code, requirements, instruction, execution conditions and
verified scope against `previous_result_id`. Without a baseline all changes must
be `unconfirmed`. Evidence has a fixed revision or content fingerprint; a mutable
URL plus fingerprint identifies a snapshot but does not promise to reconstruct
its full text. Private/unavailable evidence retains a reason without a private URL.

Decisions contain input result IDs, a short reason, concrete next-action plans,
reuse/recheck scopes, unresolved work, resume conditions and a typed source:
settings, human instruction or parent choice. An initial decision instead uses
fixed request/agreement evidence in `basis`, with no fabricated predecessor result.
Plans have their own random IDs; each branch uses a separate plan/action.

Actions reference the decision and plan. If no decision was supplied, both IDs
are null and `decision_missing_reason` is mandatory; no decision is invented.
State updates append action snapshots linked by `previous_action_id`, preserving
their scope, decision, plan and operation. An earlier requested/running action
snapshot is the source of a result; a later terminal snapshot links that result
in `result_ids`. Pointing both sides at the same snapshot would create a cycle.
Results from actions marked only `decided_not_executed` are rejected.
Action histories retain confirmed execution across `unknown` snapshots. After
execution was observed, the same action cannot return to requested or pre-start
rejection states.

Corrections append a target reference and reason, optionally referencing a separate
replacement record of the same kind and scope. Original records remain present;
the graph does not silently replace them or treat corrections as new observations.

## Missing values, times and usage

Availability is either `{status: observed, value: ...}` or
`{status: unavailable, reason: ...}`. Unknown times, durations, usage and effective
settings are never replaced with zero, the selected model or the current time.
Observed zero remains valid. Occurrence/receipt times use availability values;
`recorded_at` is the actual recording time. All observed times require a timezone.

Selected model/effort retains the specification source; observed effective values
are independent. Measurements retain their evidence. Usage retains per-turn versus
cumulative scope and a public counter key; neither grouping nor this package adds
cumulative counters, estimates cost or interprets cached tokens as billed usage.

Missing final reports retain a reason such as `missing_final`. A pending decision,
unrecorded parent verification, decided-but-unexecuted action, pre-start rejection
and pending publication are distinct fields/states. Their meaning is not inferred
from runtime exit status.

## Capture surfaces and limits

Each result's evidence identifies `capture_source`, artifact and the fingerprint
of the observed snapshot. Private evidence stays explicitly unavailable publicly;
a fingerprint alone is not a content archive. Canonical parent comments and
published review/worker-log artifacts also retain fixed public evidence where
available. Outboxes keep private delivery inputs; they are never publication units.
Parent response summaries project public fields instead of copying assignments
or arbitrary nested state. Private provenance IDs are registered before capture;
the complete response and error details remain private evidence.

| Surface | Observed source and boundaries |
|---|---|
| `run-worker` | Parent CLI request/refusal/response; the exact bound runner's `result.json`, selected/effective settings, reported counters, end reason and final availability |
| `start-worker` / `continue-worker` | Parent CLI request/refusal/reservation; dispatcher job binding, durable cancellation/runner return, bound runner writes. Reservation is not observed startup |
| Dispatcher direct child starts | The same saved job binding and runner callbacks, including bootstrap children; no fabricated parent decision |
| `record-worker-run` / `record-worker-ended` | Explicit registration of existing runner evidence / the parent's explicit termination confirmation |
| `record-result` | Saved verification and its PR/evidence fields; explicit verification references captured results. Combined `review-request --prs` uses this same method |
| `note` / `decide-worker-plan` | Canonical comment reference / saved planning-answer outcome. They do not invent a common decision; `decide` can reference the original reason |
| `delegate`, `stop` / `resume` / `stop-worker`, `handoff` / `release` | Parent command outcomes and canonical comments; dispatcher cancellation and runner stop/recovery writes are separate facts |
| `review-prepare` / `review-request` / `review-state` | Fixed request and explicit instruction/state outcomes. Only explicit receipt/verification operations set parent verification |
| Review `run` | Existing execution/output/result/publication states, including valid output from a failed runtime, exception and public predecessor review keys. Publication preserves the original result. Reusing a consumed run is a fetch, not another AI review |
| Review `recover` / `resume-publication` / `complete-evidence` / `resolve` | Existing saved-source recovery, publication-only retry, and explicit parent verification. They retain predecessor results and never become another AI invocation |
| Review retrieval tools | Existing received acquisition receipts, including failed CI requests. Repeating the same tool/arguments under the same review binding is `retry_fetch`; only the query instruction is known unchanged |
| Merge gate `merge` | Per-PR evaluations, saved merge attempts/results and aggregate outcome. Dry-run eligibility remains distinct from an actual merge |
| Worker-log receive/publish, `worker-log-status` / `publish-worker-log` | Existing journal views, final/publication failures and confirmed main publication; publication retries use `retry_publication` and reference the preceding captured result |

Supported requests accept `--decision-id` and optional `--plan-id`. A single
matching plan is selected; ambiguous, wrong-operation and already requested plans
are rejected. Without a decision both links stay null with an explicit missing
reason. `--retry-of` references a captured result, and `--changes-file` accepts
the contract's five comparison fields. Action histories use
`previous_action_id`; separate attempts compare through `previous_result_id`.
Same-session continuations use the exact previous runtime binding. A continuation
request resolved to an initial launch retains the request and a separate
`start_ai` action. Model origin distinguishes the caller's fixed defaults from
an explicit choice even when the caller materializes a default as a runner flag.
Saved worker preflight data also compares requirement and sent-prompt snapshots
and detects changed start revisions. An unchanged commit alone does not prove
unchanged working code; unobserved conditions and verification scope stay unknown.

Uncaptured surfaces: arbitrary shell/HTTP/gh operations, direct in-process
ParentSession calls outside these CLI contexts, runner invocations without a
parent binding, and parser/identity/repository failures before a parent namespace
is resolved. No historical conversation or arbitrary past run is reconstructed.
Review fix-resolution policy and automatic recovery/model selection are unchanged.
No polling, agent restart or Git publication is added by capture.

## Explicit parent decisions

Run from the same configured parent state and assigned session:

```bash
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N decision-log-status
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N decide --spec tmp/decision.json
```

The spec supplies `inputs` (one or more captured result IDs), `evaluation`,
`reason`, and optional `next_actions`, `reuse_scope`, `recheck_scope`,
`unresolved`, `resume_conditions`, `basis` and `source_kind`. Each next-action
plan uses the schema's operation/summary/actor/target/instruction/conditions/
expected_result fields; the CLI allocates its ID. An initial decision instead
needs fixed public request/agreement evidence in `basis`. Repeating the same
spec and source snapshot in the same session returns the same decision/plan IDs.
Unused plans remain decisions about work that has not been requested.

Instead of `reason`, use exactly one `reason_ref`:

| Kind | Reference to the existing source |
|---|---|
| `note` | `body_sha256` returned by the existing note command |
| `worker_plan` | `child` and the planning command's `decision_id` |
| `model_reason` | `child`; the currently saved model-selection reason |
| `review_reason` | `run_id`; the fixed review request's reason |

The decision retains a reference/fingerprint, not another copy of the public
reason. Parent actor keys are random private-session mappings; handoff does not
relabel earlier decisions. Pass the returned decision ID on the next supported
command (or review/merge command); its later results reference the linked action.

## Capture failure and recovery

An operation saves frozen IDs, times, source snapshots and delivery records in a
private `captures/` outbox beside the parent journal before journal delivery.
Flock serializes concurrent updates; caller and runner reload the current outbox.
Capture errors emit stderr diagnostics and retain pending deliveries. A separate
private diagnostic path detects missing outbox writes or adapter failures before
a result could be constructed. Loss of the entire state filesystem can only be
reported on stderr; it cannot be durably recorded on that failed filesystem.
Capture initialization rejects invalid explicit capture inputs separately from
journal/outbox failures. Storage failures preserve the original operation even
when a decision ID was supplied, and leave a persistent missing-source diagnostic.
Delivery replay cannot clear facts lost before a result could be captured.

```bash
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N decision-log-status
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N retry-decision-capture
```

Status lists the source, action/result IDs, pending/open receipts, missing capture
diagnostics, publication state and a sanitized read-only record view. A blocked
view is not publication. Replay delivers frozen records in dependency order and
does not rerun workers, reviews, fetches or merges. Unreadable receipts and missing
source snapshots remain incomplete; no empty journal reset occurs. Adapter/source
loss may require reimporting the existing canonical evidence after repair.
These observation failures never change the original operation's exit/state.
The explicit `decide` and capture-recovery commands do fail if their own recording
or recovery cannot complete.

## Private journal and publication boundary

Construct `Journal(parent_store.directory, repo, parent)` using the existing
[parent state](../parent/README.md). The package creates one parent journal below
`decision-logs/`, separated by repository and parent. Directories are private and
files/locks are owner-only. Symlinks are rejected. Entry lists only grow; flock,
file/directory fsync and atomic replacement protect each append. Corrupt JSON,
duplicate/unknown keys, unknown versions and identity changes fail without resetting
the file. This is a local filesystem contract, not distributed ownership.

- `capture(key, record, private=...)` freezes exact input. The private context has
  sessions, runs, other identifiers, checkout roots and a nullable checkout commit.
  The record ID may be omitted; capture allocates it inside the lock. Replaying an
  identical private delivery key returns the same ID without writing. Changed input
  is rejected; callers must reuse the frozen times/scope instead of recapturing them.
- `prepare(record_id, key=..., at=...)` freezes the safe envelope or appends
  `blocked`, preserving the original. Prepare dependencies first. Retrying a blocked
  projection requires `retry=True` and a fresh delivery key, without rerunning work.
  Preparation also fixes its private transformation conditions and an integrity
  check. Journal reads validate this stored snapshot without rendering it again
  with newer private IDs. A ready projection cannot be replaced.
- `publication(record_id, key=..., status=..., at=..., evidence=..., error=...)`
  appends pending, blocked or published facts independently of capture. Published
  requires fixed public evidence and is terminal. Callers verify Git/HTTP facts;
  this library does not certify that publication actually happened.
- `public_payloads()` returns only validated safe envelopes in dependency order,
  including sanitization counts. Publishers use these units and revalidate them.
  `public_records()` is the record-only view for graph/grouping consumers. `status()`
  reports capture/publication and missing-state facts without private mappings.

Exports and pending/published publication facts check the fixed envelope against
currently known private IDs. A newly discovered private value may block export;
its capture remains saved. The caller records the publication failure with
`publication(..., status="blocked", error=...)`, preserving the original envelope.
The shared worker-log guard's historical substitution order remains unchanged.

The shared worker-log guard sanitizes prose, then rechecks all public fields and
sanitization metadata. It masks known private IDs and local paths with counted
replacements. Fixed reference URLs, identities and model metadata are checked
without rewriting their meaning. Residual credentials, unknown UUID/session
notations, unsafe URLs and control characters block preparation. This is not a
complete classifier of unknown secrets. Git paths, branches, generated READMEs and
PR text still need the publisher's public checks.

## Display aggregation

`aggregate(records)` groups adjacent machine checks or fetch retries only when the
target, scope, status, action, condition key and model settings match, comparison
links form a chain and every change is explicitly unchanged. Capture must reuse a
random condition key only for identical conditions. Unconfirmed/changed conditions,
AI starts/continuations, decisions, action snapshots and corrections are boundaries.
Fetch attempts within one retrieval action can form a group; separate actions stay
visible. Intermediate observations referenced by later decisions, verification,
corrections, action results or comparison branches remain visible even when that
reference follows the entire sequence. Only the next sample's simple comparison
link may be collapsed.
Each group preserves all record IDs, count, first/last recording times and
the last record ID. Consumers look up that record for the final result. Raw captures
and intermediate failures remain available; durations and usage are not invented.

## Git publication and navigation

From the assigned parent session, after recording a decision or receiving a group
of results, explicitly run:

```bash
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N publish-decision-log --dry-run
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N publish-decision-log
# After checking and repairing a blocked publication:
PYTHONPATH=.agents/ops .venv/bin/python -m parent --repo OWNER/REPO --parent N publish-decision-log --retry
```

There is no timer, polling or implicit publication on each capture. The command
uses the configured parent state and checks the assigned session, including for
historical publication after issue closure. It grants no implementation authority.
It prepares unprepared captures through `Journal.prepare()`, then freezes all
ready unpublished `Journal.public_payloads()` in one parent batch. Blocked captures
stay visible in status; independently safe records can still be published.
An unfinished batch is reconciled before creating another. New captures arriving
during a batch wait for the next explicit invocation after that batch merges.

The public tree keeps the existing worker files in place:

```text
.agents/logs/parents/
  README.md
  parent-<P>/
    README.md
    activity-<public-key>/
      README.md
      event-<public-record-id>.json
    child-<C>/
      README.md
      d-<existing-public-key>/
        README.md
        turn-<sequence>/
          README.md
        <sequence>-<initial|resume>/
          README.md
          # Existing instruction.md, final.md and meta.json stay unchanged.
```

Each event is the exact shared `{record, sanitization}` envelope. Every README is
derived from the public event set and existing worker files at that HEAD. The
renderer never reads private capture/publication state or calls an LLM. It orders
references causally, uses time/ID only to break ties between independent records,
and separates activities, including branches and joins. Tables show
**時刻・対象 | 結果 | 親の判断と理由 | 次の行動・実行状態 | 根拠**.
Results, decisions, action snapshots and corrections retain their own links and
reverse references. Text is escaped; captured prose cannot inject links or HTML.
Every page has hierarchy links, exact record membership and recording-time range.
Unknown final reports, undecided results and unexecuted plans remain explicit.
Auxiliary times/settings/usage are available in a disclosure without adding counters.
The stable `turn-<sequence>/README.md` never guesses initial/resume from sequence.
When worker files arrive later, it links both ways with their existing folder's
README; the earlier turn address remains valid, including an initial retry after
a pre-start refusal. Worker instruction/final contents are linked, not duplicated.

Legacy turn navigation is generated for parents with new records, with links to
their existing instruction/final and **導入前・判断未記録** where no new decision
record exists. Other worker-only parents keep their existing directory links;
this does not bulk-convert their historical logs.
The legacy notice explicitly leaves introduction time versus pending/absent
capture unconfirmed when the public snapshot cannot distinguish them.
A failed turn can have a README
without pretending that a worker final was published. A public snapshot cannot
count private pending records or prove its own main inclusion: every page's
**公開待ち** notice directs readers to `decision-log-status` for that reconciliation.
Publication facts do not trigger a README rewrite after merge.

## Publication exception and recovery

This is a distinct exception from the [worker three-file exception](../worker_logs/README.md#専用prと限定merge例外).
The dedicated branch is `decision-log/parent-<P>/<random-batch-key>`; detached
publication worktrees are created only below the original repo's
`.claude/worktrees/decision-log-<batch-key>-<revision>`. Each revision is one commit
whose sole parent is its pinned main. The command may create and merge this log PR
without Codex review, `Python` or `AGENT_AUTO_MERGE` only after checking:

- The complete raw Git diff, old/new modes and blob bytes. New events must use
  their canonical parent/activity/ID paths and match the frozen journal envelopes.
  Existing events and all worker files are immutable. Deletions, renames, symlinks,
  executable files, gitlinks, extra files and code/rule changes are rejected.
- The complete schema, graph, metadata, public text, paths and links. Required
  READMEs must exist and match regeneration from that PR's HEAD byte for byte;
  arbitrary text, missing pages and orphan README changes fail closed.
- Origin/repository, branch, fixed marker, exact HEAD, main base ref, changed-file
  count and every paginated GitHub PR file/status, followed by a fresh PR check.
  The normal merge gate is unchanged: normal or mixed PRs still require review and
  successful `Python` at their own HEAD.

Before merging, fetch current main and regenerate from its full union of records.
If main advances, create a fresh verified revision and update the same PR branch
with an exact lease. Three observed advances yield `pending / main_advanced` for
an explicit later retry, without waiting or polling. Other parents' and children's
events and links are retained. A stale GitHub `base.sha` is a snapshot, not a reason
to erase main updates. The merge is HEAD-bound. Confirm the actual merge tree's
generated bytes, main ancestry and main's saved envelopes before recording success.
An external update between the final fetch and GitHub's merge is checked again in
the merged tree; a noncanonical result stops at `readme_refresh_required` instead
of claiming success. An explicit `--retry` retains that merged PR in the private
batch history and creates a `-repair-<number>` branch with the same frozen envelopes.
Its PR can change only byte-exact regenerated READMEs when those records are already
on main. It cannot add or modify an event to manufacture a repair. Once canonical
navigation is saved, repeated publication creates no further PR.
The same explicit refresh handles worker files arriving after the batch merged,
even if no new capture record is pending; it does not manufacture capture facts.

The private `publication.json` beside the capture journal keeps all batches,
revisions, attempted mutations and diagnostics under flock and durable atomic
writes. `Journal.publication()` appends per-record pending/blocked/published facts;
no publication command is sent through capture, so it cannot produce another
publication record. Commit loss reuses an exactly verified commit. Push, PR creation
and merge loss reconcile the same branch/marker/HEAD; ambiguous POST/merge is never
blindly repeated. An observed merge whose per-record journal append was interrupted
is reconciled before choosing another batch. Dirty worktrees and corrupt journals
are not automatically reset; inspect and repair only the affected publication.
Clean publication worktrees are removed after confirmation; dirty or unrecognized
worktrees are retained and reported as `retained_worktrees`.

`--dry-run` reads prepared envelopes and local `origin/main`, validates generation,
and reports counts. It does not prepare new captures, fetch, write journal/refs,
create worktrees, or use GitHub. `saved_to_main` is true only when all current
captures have confirmed published facts; a merged batch can still leave newer or
blocked captures unpublished. Pending with exit 0 is not publication success;
errors or blocked captures return exit 2.

The exact workflow patterns live in `ci.yml` and `pull-request-labeler.yml`; ignore
rules live in `.gitignore`. They cover the existing three files and the new event
and hierarchy README paths, never the publisher implementation or arbitrary raw
logs. Native GitHub path-filter limits still apply; missing CI cannot bypass the
normal gate. Live workflow suppression and GitHub rendering must be checked after
the implementation merges, as part of #1817.

batching, concurrent main updates, exact regeneration, rejection and response loss.
