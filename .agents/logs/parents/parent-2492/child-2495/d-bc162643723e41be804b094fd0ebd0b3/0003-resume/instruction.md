# 正式レビュー（round 1）のmajor指摘への対応（親 #2492）

PR #2498（HEAD b1011e406）の正式レビューで、major指摘が1件出た。親はこれを採用する。

## 指摘

**同じIoUの候補があると、予測の行順だけで姿勢スコアが変わる。**

レビュアーの再現は次のとおり。

- 参照1人に、同一BBoxの候補を2件渡す。
  - スコア0.9の候補には、正解と一致する関節を与える。
  - スコア0.2の候補には、欠測の関節を与える。
- 候補の行順だけを反転すると、Recall@IoU 0.50/0.75 は1.0のままだった。
- 一方、coverage付きOKSとPCKは1.0から0.0に変わった。

姿勢の採点はIoU 0.50での割当を使うが、同じIoUの候補の選び方が決まっていない。そのため、#2487・#2490 のモデルや推論backendごとに候補の並べ方が違うと、比較結果が変わってしまう。
該当箇所: `src/tennis_scene/evaluation/player_pose/scoring.py` の `_score_frame`（L164-L200）と `match_iou`

## 直し方の方針（親の指定）

- 採点結果が候補の入力順に依存しないようにする。割当の前に、候補を正準順序に並べてから照合するのが簡潔。
- 同率時の優先順位を共通規約として明文化する。
  1. 検出スコアの高い順（COCOの慣行と同じく、高スコアの候補を優先する）
  2. BBox座標 (x1, y1, x2, y2) の辞書順
  3. それでも同じなら関節配列の辞書順
- 規約は採点APIのREADMEとknowledgeの記録に書く。
- score閾値で絞った各レベルにも同じ規則が効くことを確認する。
- 単体テストを追加する。
  - レビュアーの再現ケースが、どちらの行順でも同じ結果になること。
  - 候補が多い合成フレームで行をランダムに並べ替えても、全指標（Recall、score別Recall、OKS、PCK、pixel誤差、coverage）が完全に一致すること。
- 公開済みの ViTPose smoke を新しい採点器で再採点し、値が変わったかどうかを記録する。変わった場合は、PR本文とknowledgeの数値を更新する。
- ベンチマーク実体（manifest・疑似GT）は変えない。採点器の修正なので、manifest ID・sha256は変わらないはず。変わる場合は理由を親に返す。

## 進め方

修正・テスト・pre-commitを通してpushし、PR本文の「実行証拠」を新HEADで更新する。そのうえで、新HEADのCIを待つ宣言（`kind: "ci"`）で終える。最終行の `PARENT_RESULT` は1行の正しいJSONにする。

下流（#2487・#2490）は、この修正後のheadを取り込んでから再採点する。下流への連絡は親が行う。
