# #2487 edgecrafter: TRT16 の精度低下の原因を先に調べる

前回の報告（push `82ddda3c2`）を受け取った。採点と失敗記録の作りは承認する。ただし TRT16 の結果をこのまま比較図に載せる前に、原因を調べてほしい。

## 何が問題か

| モデル | PT16 Recall@0.50 | TRT16 Recall@0.50 |
|---|---:|---:|
| ECDet-L COCO | 97.61% | 64.88% |
| ECDet-X COCO | 97.58% | 70.29% |
| ECDet-L O365 | 98.19% | 63.02% |
| ECDet-X O365 | 97.97% | 65.88% |
| ECPose-X O365 | 40.09% | 9.99% |

FP16 の丸めで Recall が30ポイント落ちることは考えにくい（DINO の TRT16 は精度をほぼ保った）。変換・engine の profile・前後処理・出力の読み方のどこかに不具合がある疑いが強い。ECPose-L は PT16 と TRT16 がほぼ同じなので、ECDet 4重みと ECPose-X に共通する違いを探す手がかりになる。

## 調べること

1. 固定の数枚（代表 clip から人数の多い画像を数枚）について、**同じ前処理済み入力テンソル**を PT16 と TRT16 に入れ、生出力（logits・box）を比べる。batch 1 と batch 2 の両方で、batch 2 は1枚目と2枚目を入れ替えても結果が変わらないかも見る。
2. 疑わしい点を順に切り分ける。例:
   - batch 2 で trace し直した engine の profile と、出力 tensor の shape・stride・並びの読み方（2枚目の slot や padding を誤読していないか）
   - 入力の正規化・色順・resize が PT16 経路と同じか
   - score 閾値・top-k・NMS など後処理の設定が PT16 と同じか
   - 特定の層で FP16 のオーバーフロー（inf・nan）が出ていないか。TensorRT の層ごとの精度指定で、一部の層だけ FP32 にして切り分けるのはよい（変換の診断で、計測ではない）
3. PT32 の PyTorch 推論はしない（ユーザー判断）。比べる相手は PT16。
4. GPU を使う診断は training queue に入れる。小さい job にまとめ、待機中の速度ジョブ6件を取り消さない。

## 原因が分かったら

- 直せるなら、engine を作り直して TRT16 の精度ジョブを入れ直す。engine の sha256 が変わるので、TRT16 の速度もその engine で測り直す（いま待機中の速度ジョブのうち TRT16 の値は、古い engine のものとして扱い、記録に engine sha256 を残す）。
- 直せない、または原因が特定できないなら、そのことを根拠付きで記録し、TRT16 の精度は「変換の不具合の疑い、原因未特定」と明記して比較図の注記に回す。黙って載せない。

## 最終回答

原因（または切り分けた範囲）、入れた job、push した HEAD を書く。待機には、いま queue にある速度ジョブ6件（`i2487-*-fixed-speed-13e508cb7`）と、新しく入れた job をまとめて `PARENT_RESULT` の `waiting` / `queue` の `job_ids` に入れる。
