## 親の判断: 削除可否の判定方式を変える

#1953・#2034・#2052 のレビューで、ホスト全体のプロセス森から「対象由来の孤児がどこにも残っていない」ことを証明する方式に、PID再利用・reparent・setuid・列挙順などの競合が繰り返し見つかっている。この方式は原理的に閉じきれないうえ、無関係なプロセスを不明に巻き込んで実ホストで削除を止める（今回の6件）。合意（#1893）が求めるのは「使用中でも免除せず、管理可能なジョブ・親子を停止して状態を更新する」「停止・削除の失敗を成功扱いにしない」で、worktree を離れたプロセスの不在をホスト全体で証明することは求めていない。

新しい方針:
1. **削除の成功条件（ゲート）**: 隔離（`.expired-<id>` への rename）後に、隔離したパス配下を参照するプロセスが同じユーザーの範囲で1つもないこと。参照は `[local path]`・`root`・`exe`・`fd/*`・`map_files`（または `maps`）で判定する。参照を確認できないプロセス（権限不足など）が隔離パスを参照している可能性を排除できない場合だけ失敗にする。参照が残れば、停止を試みてから再確認し、残れば失敗として記録する（成功扱いにしない）。
2. **管理可能なジョブの停止**（parent CLI の担当・委任、共通ランナーの run、training queue、dispatcher）は、現行どおり行う。runner記録の探索範囲（#2025）と、記録なし旧委任の終了記録も維持する。
3. **native プロセスの停止**: 対象worktree を cwd などで参照しているプロセスと、停止準備で観測できたその子孫は、現行の pidfd・SIGSTOP・SIGKILL で停止する。ただし、ホスト全体での「孤児の不在証明」（`uncertain`・`discovery_uncertainty`・v2/v3 証拠の不明PIDによる失敗の維持など）は、削除可否のゲートから外す。観測できた子孫の停止に失敗した場合（生存を確認できたのに止められない）は失敗とする。
4. 不要になる複雑な判定・状態（不明PIDの永続証拠と再実行時の失敗維持など）は、残す理由がなければ削除して単純にする。既存の証拠ファイルがあっても新方式の判定を妨げないようにする（移行方法をPR本文に書く）。
5. README の停止・削除の節を新方針に合わせて書き直す。
