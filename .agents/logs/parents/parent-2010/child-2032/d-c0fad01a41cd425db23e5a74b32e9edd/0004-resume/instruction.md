# #2032 の配送 fence を PR #2084 に追加し、`Closes #2032` にする

PR #2084（Project 通信・board 表示・Codex 探索のロック外化、`References #2032`）は完成しています。残りは board 配送の担当固定（fence）です。前提だった #2031（PR #2056）と #2040（PR #2054）、#2114（PR #2116）・#2126（PR #2131）の merge gate 修正は main にマージ済みです。

## 人間が決めた方式（2026-11-14）

記録: https://github.com/Motoki0705/tennis-lab/issues/2013#issuecomment-6885719804

- board の配送は、registry.lock の代わりに、**担当変更だけを止めるホスト共通のロック1つ**で担当を固定する。配送中も status や通常の更新は止めない。
- 強制引継ぎ（`handoff --recover`）と worktree 期限切れによる強制解除も、**送信の完了を待つ**。無関係な親の担当変更も、1回の配送試行の完了を待つことになるが、それでよい。

## 依頼

1. `codex/board-project-io` を最新の origin/main へ rebase する。#2056・#2054・#2116・#2131 との衝突を、両方の契約を保って解消する。
2. 上の方式で配送 fence を実装する。担当変更が起き得るすべての入口（parent の register/handoff/release、`handoff --recover`、dispatcher、worktree の期限切れ処理など）が、このロックに参加すること。配送は registry.lock を持たずに、固定した担当で送信する。commit-before-notify と、受理が不明なときに再送しない契約を保つ。ロック順（このロックと registry・routes）を一意に決め、デッドロックしないこと。
3. 回帰テスト: 配送中に別プロセスが registry.lock を取れること。配送中に担当変更（通常・強制・期限切れ）が送信完了まで待つこと。配送が終われば担当変更が進むこと。配送中に担当が変わった場合に旧担当へ送らないこと。テストは設計してから書く。
4. PR 本文を `Closes #2032` に変え、配送 fence の説明と検証を追記する。関連テストと pre-commit を通し、push して対象HEADの CI（Python）の成功を確かめる。

正式レビューは PR ごとに1回だけです（人間の判断）。PR #2084 はまだ正式レビューを受けていないので、この追加の後に1回レビューします。

共有の GitHub API 上限は逼迫しがちです。検証は fake で行い、実 GitHub は push・PR 更新・CI の確認だけに使ってください。短い間隔の polling はしないでください。時間の上限は6時間。止めてよいのは、方式どおりに実装すると既存契約と両立しない点が見つかり親の判断が要る場合と、6時間を超えた場合だけです。止める場合は、済んだ範囲・未了の受入条件・次の一手を報告してください。
