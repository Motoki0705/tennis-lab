## この委任の位置づけ

親 #1698 の子。先行の2件はmerge済み。

- #1706（PR #1742）: `video_ball_annotation.v3` の契約・reader・利用判定（`src/tasks/ball_detection/annotation/video`）。
- #1707（PR #1745）: ローカル動画を白紙注釈要求として登録するAPI。元収録group（`source.recording_id`）と公開選択（plan の `publish_dataset`）を固定する。

この子は、保存済みのv3注釈から、画像・教師・由来・group/splitを持つ不変のdataset snapshotを `data/ball_detection/` 形式で公開し、学習readerで読めるようにする。公開オプションのCLI配線は #1713 が行う。

## 実装してほしいこと

担当issue本文の変更範囲と受入条件をすべて満たし、PRを作成するところまで行う。mergeは親が行う。

- v3の読込と利用判定は #1706 の reader と usage をそのまま使い、公開側で状態の意味を再定義しない。三角測量や平滑化の後の点ではなく、元のv3注釈から直接公開する。
- 位置のある推定点は教師として有効にする。観測と推定は同じ重みとし（親issueでの初期設計案）、黙って低重み化したり、旧来の observed_only へ戻したりしない。最終unknownは教師maskで無効にし、未処理を含む注釈は完了扱いにせず公開を拒否する。
- 教師の対象が active_ball であることをsnapshotに記録する。no_active_ball と out_of_frame は「プレー球の不在」としてだけ使い、全ボール検出器向けの既存教師へ無条件の負例として混ぜない。
- 同じ元収録の全cameraと関連clipを一つのgroupにまとめて同じsplitに置く。既存のholdout・評価groupをtrainへ移さない。
- 注釈schemaの版（v3）とsnapshotの版名を分ける。公開receipt、冪等な再送、中断からの原子的な復旧は既存のpublisherの仕組みに接続する。注釈は公開しなくても残る。学習jobは起動しない。
- 公開方針（active_ballの対象の意味、状態別の正例・負例・除外、推定点の重み、画像の保存方式・元解像度・PTS、注釈revisionとsnapshot版、重複と修正の扱い、公開範囲）をREADMEとPR本文に書く。

## テスト

tests/README.md のテスト作成方針に従い、担当issueの各受入条件の「検証方法・証拠」に書いたテストを実装する。native画像と対象frameを照合し、推定点の位置教師が有効、unknownが無効であることをreaderの出力まで検証する。学習の起動はspyで呼出しがゼロであることを確認する。

## 実行環境の制約（重要）

このマシンはGPUなし、RAM約4GBのラップトップ。`pytest -n auto` を全体で走らせるとメモリが尽きる恐れがある。変更範囲のテストは `-n 0` または `-n 2` で、対象ディレクトリに絞って実行する。全体テストはCIに任せる（PRへのpushごとに実行され、`Python` jobの成功がmerge条件）。PR作成後にCIの結果を確認し、失敗があれば修正する。実データでの公開は後続 #1715 の範囲なので行わない。

## 作業量と終了条件
