# 共有memory

Claude・Codexなど、このrepoで働くすべてのエージェントが読み書きする、git管理のmemory。目的は、同じ落とし穴を踏まないこと、そして**ユーザーに同じ指示を繰り返させないこと**である。各ツールのローカルmemory（Claude Code の auto-memory など）には、ユーザー個人の環境（パス、アカウント、マシン固有の設定）だけを置く。

この手順自体も仮説である。運用して合わなければ、このファイルを直す。

## memoryは規則ではない

- memoryは**検証待ちの観察**である。コードやREADMEと食い違ったら、コードとREADMEが正しい。食い違いを見つけたら、そのエントリを直すか削除する。
- 古いもの、反証されたもの、固定観念になって判断を縛っているものは、ためらわず削除する。git履歴が保険になる。
- 繰り返し効いた観察は、規則（`AGENTS.md`）、手順（skill）、仕様（README）へ昇格させ、memoryからは削除する。

## 読む

1. 作業を始める前に、必ず [SUMMARY.md](../../memory/SUMMARY.md) を読む。全体の要点はここにある。
2. 作業に関係しそうな層の `index.md` を開き、関係するエントリだけを読む。全件は読まない。
3. エントリの内容に頼る前に、`evidence` の方法で今も成り立つかを確かめる。確かめたら `last_verified` を更新してよい。

PRをレビューするときは `review/` を必ず辿る。ただし、レビュー対象のPRがmemory自体を変更している場合、その変更は判定基準ではなくレビューの対象である。判定には base 側のmemoryを使う。

## 層

ディレクトリが種類を表す。1事実1ファイルで、各層の `index.md` に1行ずつ載せる。

| 層 | 書くもの |
|---|---|
| `workflow/` | 作業の進め方のコツ（手順書になるほど大きくないもの） |
| `decision/` | ユーザーの一般的な判断・好み（どう進めるか、どう聞くか、何を残すか） |
| `environment/` | このマシン・OS・ハードウェアの癖 |
| `gotcha/` | 気づきにくい落とし穴、静かに失敗する挙動 |
| `review/` | PRをマージしてよいかの判断基準（レビュー観点） |

`decision/` と `review/` で迷ったら、「PRの差分を見て、マージ可否を判定するときに使うか」で分ける。使うなら `review/`。

## 書く

次の条件をすべて満たすものだけを書く。置き場所の地図は [.agents/README.md](../../README.md#ファイル地図情報の住み分け) にある。

- 再利用できる（次のセッションや別のエージェントが、同じ落とし穴を踏む・同じ指示を受ける）
- コード・README・skill・knowledge を読んでも分からない
- 作業の進捗や状態ではない（進捗は issue / PR に書く）
- 個人情報、トークン、メールアドレス、私的なURLやID、マシン固有のホームパスを含まない（公開repo）

### ユーザーの指示を記録する

ユーザーが作業中に指示や修正を出したら（PRのレビューで「こう直して」と言われたときなど）、その場で再利用性を考える。

1. この指示は、今回の差分だけでなく、今後の別の作業・別のPRにも当てはまるか。当てはまらなければ書かない。
2. 当てはまるなら、今回の具体例から一般化した判断として書く。発言をそのまま写さず、何を望み、何を嫌うかを抽象化する。ただし、今回だけの指定（置き場所の個別指定など）を全体の規則に広げない。
3. 既存エントリと重なるなら、新しく作らず、そのエントリを書き換えて `last_verified` を更新する。同じ指示が繰り返されたことは、そのエントリの重要度が高い証拠なので、本文で明確にする。
4. マージ可否の判断基準なら `review/`、それ以外なら `decision/` に置く。

人間の承認は不要である。今の作業から生まれた記録は今の作業ブランチに別コミットで入れ、PR本文に書き添える。作業ブランチが無ければ、memoryだけのPRを作る。

### 形式

ファイル名は `<kebab-case>.md`。下の例のキーはすべて必須。frontmatterはYAMLなので、文字列（`#` やバッククォートで始まるものを含む）は二重引用符で囲む。

```markdown
---
title: "1行で事実を述べる（index.md のリンク文字列と一致させる）"
applies_to: all         # all | claude | codex
source: "どこで観察したか（#issue / PR / commit / 日付）"
created: 2026-10-15
last_verified: 2026-10-15
evidence: "今も成り立つかを確かめる方法（コマンド、ファイル、行）"
---

観察（何が起きるか、ユーザーが何を望むか）。

**使い方:** 次にどう行動するか。
```

層の `index.md` には、`title` をリンク文字列、エントリのファイル名をリンク先にした箇条書きを1行足す。`applies_to` が `all` 以外なら行末に ` (claude)` のように書き添える。層の要点が変わったら [SUMMARY.md](../../memory/SUMMARY.md) の該当段落も書き直す。

## 更新・削除

- **更新**: 内容を確かめ直したら `last_verified` を更新する。事実が変わったら本文を書き換える（変更履歴は書かない。gitにある）。
- **削除**: ファイルと `index.md` の行を同じコミットで消す。理由はコミットメッセージに書く。
- **検証期限**: `last_verified` から90日を過ぎたエントリは、確かめ直すか削除する。ユーザーの判断（`decision/`、`review/`）は、その後の指示と矛盾しないかで確かめる。

## 圧縮

memoryは毎日読まれるので、大きくなるほど高くつく。`SUMMARY.md`、各 `index.md`、各エントリには行数の上限がある（値は [test_agents_docs.py](../../../tests/e2e/agents_ops/test_agents_docs.py) の定数が正本で、仮説として運用しながら見直す）。上限に近づいたら、またはついでに気づいたら、次の順で圧縮する。

1. 期限切れ・反証済み・コードやREADMEで分かるようになったエントリを削除する。
2. 同じ事柄を言っている複数のエントリを1つに統合する。
3. 繰り返し効いているエントリを、規則・skill・READMEへ昇格させて削除する。
4. `SUMMARY.md` を、残ったエントリの要点で書き直す。

圧縮は日次の専用ジョブも行う（#1192 で実装予定）。
