# 担当と合意

## どこから始めるか

| `status` とIssueで確認した状態 | 次の操作 |
|---|---|
| 新規担当 | 引受を指示された親セッション自身が `register --summary`。要約は表示幅24桁以内で現在の仕事を書く。担当を登録したあと、合意または自律着手の根拠を確認する。 |
| `current_session_is_owner=true` | `phase`、`input_changes`、既存PR・委任・停止理由を読み、済んだ作業の続きから進める。作業の焦点が変わったら `summary --text`。 |
| 別のセッションが担当 | 移管の指示と前任の状態を照合して引き継ぐ。担当とワーカーの実行記録は共有stateにある。 |

手動の実行根拠は `agree --spec` に目的・範囲・期待動作・受入条件と、人間の確認発言の原文を保存する。会話ですでに明確な指示はそのまま使う。仕様が不足していれば、その判断に依存する作業だけを保留し、人間に確認する。

agyは[手動の対話ルート](../../../ops/parent/README.md#agyの手動親)で担当する。Herdrを使う場合は
[専用ランチャー](../../../ops/herdr_labels/README.md#agyの手動起動と表示)で起動してから登録する。

親Issueの本文補足が `pending` で合意を保存できないときは `wait-supplement`。対象workflowの終了後もpendingなら、表示されたrun・確定ラベルを照合する。[補足の状態](../../../ops/issues/README.md#親issueの補足追加状態)

## 要件変更

- 本文編集・追加コメントは変化の通知。変更前後の意味と影響する成果を読み、目的・範囲・受入条件・権限に実質変更があれば合意を更新する。合意内の作業順・担当・調査方法は親が決める。検証は変更の影響が及ぶ範囲をやり直す。
- 人間による親全体の実行根拠の取消しは `basis-revoke`。一つのIssueの保留・解除には `stop` / `resume` を使う。`checking` は確認中という表示で、すでに有効な合意は維持される。

## 引継ぎ

前任は `handoff --note-file` に達成済み・未達の受入条件、PRと確認済みHEAD、ワーカーの停止・回収状況、次の操作を残す。後任が同じIssueで `handoff --accept` し、`status` で引き継いだ記録を読む。前任が予期せず止まった場合は、担当指定と停止の証拠を確認して `--accept --recover`。session IDやprivateなrunパスは公開コメントに載せない。

## 採用提案

レポート由来の作業は `receive-proposal` に元のレポート・提案IDを渡し、その提案について確認した要件を `agree` に結び付ける。終了時改善から取り出した親は `agree --improvement-approval` に専用の人間判断IDを渡す。dispatcherからの予約は [自律親](dispatch.md) で受理する。
