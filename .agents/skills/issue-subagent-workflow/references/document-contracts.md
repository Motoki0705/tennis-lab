# Document contracts

Every formal artifact begins with the Issue number, current attempt, and status. Implementation, preflight, and test artifacts also record the current test-cycle number. Remove placeholders before applying the corresponding verdict or transition.

## `issue.md`

Generated by the initializer and immutable during an attempt. The exact `## Acceptance checklist` is normalized to stable IDs `AC-001`, `AC-002`, and so on. Checklist count and SHA-256 are recorded in both `issue.md` and `state.toml`.

The normalized checklist is authoritative. Original checkbox state is metadata only.

## `state.toml`

Schema version 4 records:

- frozen Issue and checklist identity;
- attempt and phase;
- feasibility verdict;
- preflight and independent test cycle/verdict state;
- repeated-RETURN review state;
- task status, final verdict, and blocker details.

New tasks start at `phase = "feasibility"`. `status = "blocked"` requires `verdict = "BLOCKED"`, a valid `block_kind`, and a concrete `block_reason`. Refreshing the upstream Issue starts a new attempt at feasibility.

Schema version 3 is normalized to version 4 as a legacy task. Its previous work remains usable, but any subsequent implementation cycle must write and pass preflight before the next independent Tester verdict.

## `00-feasibility/feasibility.md`

Owned only by the parent. Required sections:

- Allowed and prohibited changes
- Required checks and baseline
- Breaking-change and compatibility impact
- Acceptance checklist feasibility
- Constraint conflicts
- Final feasibility verdict
- Blocker resolution required

The matrix contains exactly one ordered row for every AC ID and exact Issue item text. Each row is `FEASIBLE`, `BLOCKED`, or `UNKNOWN` with the required write scope and evidence.

- PASS requires every row to be FEASIBLE and a standalone `PASS`.
- BLOCKED requires at least one BLOCKED or UNKNOWN row, concrete conflict evidence, required resolution, and a standalone `BLOCKED`.

## `01-exploration/exploration.md`

Required sections:

- Scope and Issue interpretation
- Relevant files and symbols
- Entry points and execution paths
- Data, configuration, and interface contracts
- Existing tests and fixtures
- Invariants and compatibility constraints
- Risks and likely impact radius
- Unresolved questions
- Evidence table distinguishing fact, inference, and unknown

A path list without traced behavior is insufficient.

## `02-planning/plan.md`

Owned only by the parent. It includes the frozen checklist hash and exactly one ordered mapping row per AC item. Each row maps to an implementation action and authoritative validation method.

The plan also records the ownership matrix, deterministic preflight checks, focused checks, canonical required-check command, baseline failures, and allowed test ownership. Merely mentioning AC IDs in prose does not satisfy the mapping contract.

## `03-implementation/implementation.md`

Required metadata:

- Issue number
- current attempt
- next test-cycle number
- status

Required sections:

- Assigned ownership
- Files and symbols changed
- Behavior implemented
- Plan deviations and rationale
- Commands and results
- Known limitations and remaining risks
- Handoff

The designated integrator replaces this file after all Implementers join. On a repair, it records how the concrete preflight or Tester findings were addressed. It must not conceal a scope conflict or weaken tests.

## `03-implementation/preflight.md`

Owned by the artifact integrator, not the independent Test Writer. Required metadata:

- Issue number
- current attempt
- next test-cycle number
- status

Required sections:

- Changed scope
- Deterministic policy checks
- Focused checks
- Canonical required checks
- Baseline comparison
- Commands and exact outcomes
- Final preflight verdict
- RETURN implementation findings

The final verdict is one standalone `PASS` or `RETURN`.

- PASS means deterministic integration checks and the canonical required checks succeeded for the integrated revision.
- RETURN means a production or integration failure is already proven. Findings must be actionable. It does not increment the independent test cycle.

Raw output may live under `logs/`; the artifact records command, exit status, concise outcome, and path.

## `03-implementation/tests.md`

Owned by one independent Test Writer after preflight PASS. Required metadata:

- Issue number
- current attempt
- current test-cycle number
- frozen checklist hash
- status

Required sections:

- Acceptance-checklist-to-test mapping
- Tests added or changed
- Normal, boundary, invalid, and regression cases
- Commands and exact outcomes
- Failures encountered
- Untested risks and reasons
- Final test verdict
- RETURN implementation findings

The mapping table contains exactly one ordered row for every AC ID and exact Issue item text. Requirements not provable by automated tests identify the authoritative evidence the Validator should collect.

The final verdict is one standalone `PASS` or `RETURN`. RETURN findings include exact failing commands, observed behavior, affected AC IDs, and required production behavior.

## `04-validation/validation.md`

Required sections:

- Frozen Issue and checklist hashes
- Inspection scope and revision
- Acceptance checklist verification matrix
- Exactly one ordered row per AC item
- Direct evidence with `PASS`, `FAIL`, or `NOT VERIFIED`
- Code evidence
- Runtime and test evidence
- Regression and repository-rule checks
- Final verdict
- RETURN exploration questions

Validator PASS requires every row to be PASS. Validator RETURN requires at least one FAIL or NOT VERIFIED row. The helper rejects missing, duplicated, reordered, unknown, or text-mismatched rows.
