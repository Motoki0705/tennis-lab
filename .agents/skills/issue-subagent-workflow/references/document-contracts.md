# Document contracts

Every artifact begins with the Issue number, current attempt, and status. Remove all placeholder text before advancing phases.

## `issue.md`

Generated by the initializer and immutable during an attempt. The Issue body must contain at least one Markdown task-list item. The initializer normalizes those items into an ordered acceptance checklist with stable IDs `AC-001`, `AC-002`, and so on, and records a checklist count and SHA-256 in both `issue.md` and `state.toml`.

The normalized checklist is the authoritative acceptance matrix. The original source checkbox state is metadata only; `[x]` does not prove implementation and `[ ]` does not prove failure. Duplicate or missing checklist items make initialization fail. Refreshing the Issue requires a new exploration attempt.

## `01-exploration/exploration.md`

Required sections:

- Scope and Issue interpretation
- Relevant files and symbols
- Entry points and execution paths
- Data, configuration, and interface contracts
- Existing tests and fixtures
- Invariants and compatibility constraints
- Risks and likely impact radius
- Unresolved questions
- Evidence table distinguishing fact, inference, and unknown

A path list without traced behavior is insufficient.

## `02-planning/plan.md`

Owned only by the parent. Required sections:

- Frozen Issue hash and acceptance-checklist hash
- Acceptance checklist mapping with every AC ID and exact item
- Planned implementation and validation method for every AC item
- Planned files and symbols
- Implementation work units and exclusive ownership
- Independent test work unit
- Ordered execution plan
- Validation strategy
- Explicit non-goals and prohibited changes
- Risks, rollback, and open decisions

Every AC item must map to at least one implementation action and one authoritative validation method. The state helper rejects advancement when an AC ID is missing from the plan.

## `03-implementation/implementation.md`

Required sections:

- Assigned ownership
- Files and symbols changed
- Behavior implemented
- Plan deviations and rationale
- Commands and results
- Known limitations and remaining risks
- Handoff to test writer and validator

Do not claim acceptance; describe evidence and changes.

## `03-implementation/tests.md`

Required sections:

- Acceptance-checklist-to-test mapping containing every AC ID
- Tests added or changed
- Normal, boundary, invalid, and regression cases
- Commands and exact outcomes
- Failures encountered
- Untested risks and reasons

Every AC ID must be addressed. For requirements that cannot be proven by an automated test, identify the authoritative runtime, artifact, inspection, or integration evidence the validator must collect. Tests must demonstrate behavior rather than mirror implementation structure. The state helper rejects validation entry when an AC ID is absent.

## `04-validation/validation.md`

Required sections:

- Frozen Issue hash and acceptance-checklist hash
- Inspection scope and inspected revision
- Acceptance checklist verification matrix
- Exactly one ordered row for every AC ID and exact Issue checklist item
- A verdict of `PASS`, `FAIL`, or `NOT VERIFIED` with direct evidence for each row
- Code evidence
- Runtime and test evidence
- Regression and repository-rule checks
- Final verdict: exactly `PASS` or `RETURN`
- RETURN exploration questions, when applicable

`NOT VERIFIED` or `FAIL` forces RETURN. PASS requires every AC row to be PASS, no checklist row to be missing or duplicated, the checklist hash and count to match `state.toml`, and no relevant regression. The state helper mechanically rejects PASS otherwise.
